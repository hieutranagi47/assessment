# Improvement Plan

## Context and architectural direction

`appointment_scheduler` currently contains several business capabilities in one
module: dealership configuration and local access, customers and vehicles,
service definitions, service bays, technicians and their availability, and the
appointment lifecycle. The current internal structure (`domain`, `app`,
`adapters`, and HTTP API) is a good foundation and should be retained.

The recommended target is **five business modules**, kept in the same Go
application and PostgreSQL database initially. The existing `auth` module
continues to own identity and authentication.

| Module | Responsibility |
| --- | --- |
| Dealership Administration | Dealership profile, timezone, operating hours, and dealership-scoped access roles. |
| Customer and Vehicle | Customer records, customer-dealership relationship, and vehicles. |
| Service Catalogue | Service types, duration rules, skills, bay capabilities, and service requirements. |
| Workshop Capacity | Technicians, service bays, qualifications, shifts, and time off. |
| Booking and Appointment Lifecycle | Appointment requests, lifecycle transitions, audit history, idempotency, and booking status. |

This is a modular-monolith design, not an immediate microservice plan. A module
publishes a narrow capability from `api/module`; its consumers depend on the
matching `api/module/client` interface, rather than on repository or database
models.

## Current limitations

- `appointment_scheduler` is a large bounded context. It owns dealership
  administration, CRM, catalogue, workforce, capacity, and appointment
  workflows, which may eventually need independent release and scaling.
- Scheduling currently reads and validates data from customers, vehicles,
  operating hours, service types, technician skills, service bays, shifts, and
  time off in one repository transaction. This makes changes to any of those
  concerns risky and hard to test independently.
- The technician-calendar **query joins several domains** and is likely to become
  a high-read path as dealers book appointments more frequently. Similar to the
  checking roles for authorization.
- There is no cache or dedicated read model for schedules and appointment
  history.
- Customer-facing booking and history screens would add substantially more
  read traffic to the same operational tables. A single database is not itself
  a problem, but it needs read-path measurement, indexes, and separation before
  it becomes a bottleneck.
- Appointment creation is currently strongly consistent: it uses a serializable
  PostgreSQL transaction and an exclusion constraint on resource reservations.
  This prevents overlapping technician and service-bay bookings, but couples
  booking to the other data sets.

## Short-term improvements

Keep `appointment_scheduler` as one module, with its current `domain`, `app`,
`adapters`, and HTTP API structure. The five-module map is a future ownership
map, not a required package refactor now. Keep one deployable application and
database; do not split databases or deploy microservices in this phase.

1. Preserve the current transactional reservation path while strict
   no-double-booking behaviour is still required. The serializable transaction
   and database exclusion constraint remain the final concurrency guard.
2. Create purpose-built read models for the technician calendar and appointment
   history. Do not reuse database rows or domain entities as HTTP responses.
3. Add Redis only for measured, frequently read and safely cacheable data:
   daily technician schedules, operating hours, service catalogue, and
   customer appointment-history pages. Define invalidation on appointment,
   shift, time-off, technician, bay, and catalogue changes; use short TTLs as a
   fallback.
4. Measure p95/p99 latency, database connection-pool saturation, slow queries,
   cache hit rate, and booking conflicts before selecting a new datastore.
5. Replacing join tables crossing domains.

## Long-term improvements

### Event-driven booking option

If the business accepts eventual consistency, Booking no longer needs a
cross-module transaction. A submitted booking becomes `requested`, then is
asynchronously evaluated against a capacity projection and becomes
`confirmed` or `rejected`. The user experience must explicitly support this
confirmation step, retries, and conflict handling.

```text
Service Catalogue + Workshop Capacity
                | domain events / contracts
                v
       Availability read model
                |
                v
 Booking: requested -> confirmed | rejected
```

Use an outbox pattern so a committed module change and its event are delivered
reliably. Consumers must be idempotent. A document store or other NoSQL
database may be useful for denormalized appointment history and availability
projections, but only after the query pattern and throughput justify it; it
must not become the source of truth for appointment writes by default.

This option has an explicit trade-off: two requests can temporarily choose the
same resource. It is suitable only when later confirmation, a waitlist, manual
dispatch, or compensating rejection is acceptable. If double-booking is never
acceptable, retain a small atomic reservation capability in Booking.

### Customer-facing capabilities

Expose customer booking and history through read-optimized APIs backed by the
appointment-history projection and cache. Authorize every request against the
`auth` identity and the Customer and Vehicle ownership rules; do not expose
internal dealership user or appointment models directly.

### Deployment evolution

Extract a module into an independently deployable service only when it has a
clear ownership boundary, a sustained independent scaling or release need, and
observable operational benefit. Likely first candidates are customer-facing
read APIs or availability projections, not the booking write path.

Adopt Kubernetes when the operational need is proven: multiple independently
scaled services, repeatable deployment requirements, and a team able to run
cluster observability, incident response, security, and cost controls. It is
not a prerequisite for the modular-monolith improvements above.
