# Dealership Appointment Platform — Implementation Definition

## Executive decision request

Approve the current implementation as the foundation for a dealership operations platform, with the Appointment Scheduler as its production-candidate core. It solves the operational risk that matters most: a dealership can schedule work only when the required technician and service bay are compatible, available, and not already committed.

The recommended delivery model is a **modular Go monolith backed by PostgreSQL**. This is the lowest-risk, most economical choice for the assessed scale: it keeps a booking decision and its resource reservations in one transaction, while preserving explicit module boundaries that allow the scheduler to be extracted later if evidence—not anticipation—requires it.

The proposed system design, deployment topology, service-level objectives, and capacity plan will be reviewed separately. This document defines the delivered business capability, quality bar, architectural decisions, verification evidence, and remaining decisions needed before production launch.

## Business outcome and scope

The platform gives dealership teams one trusted operational record for customers, vehicles, workshop capacity, and appointments. It is designed for multi-dealership operation while ensuring a user cannot act outside their dealership scope.

The first release is an internal employee tool. It does not yet include a customer self-service portal, payments, notifications, inventory/parts management, or dealer-management-system integrations. Keeping this boundary explicit prevents premature complexity and lets the team validate the core scheduling workflow first.

### Delivered functional requirements

| Capability | Business rule and outcome | Implementation evidence |
|---|---|---|
| Identity and access | Users can register and sign in. A single bootstrap superadmin can be created; only a superadmin can change another user’s global role. Password changes and “sign out all devices” advance a token version so existing refresh sessions cannot be reused. | `auth` bounded context; RS256 JWT access and refresh tokens; role and authorization tests. |
| Privacy-aware account lookup | Email is stored encrypted and is looked up through an independent keyed HMAC, avoiding plaintext email storage for normal account lookup. | AES-GCM encryption plus separate lookup key and automated crypto tests. |
| Dealership administration | A global `admin` or `superadmin` can create a dealership. A dealership administrator can grant an existing authenticated user one dealership role: `admin`, `staff`, `dealer`, or `technician`. | Auth is consumed through a published module contract, rather than direct database access. |
| Workshop configuration | Authorized dealership administrators manage operation hours, service types and their required skills/bay capabilities, service bays and capabilities, technicians, technician skills, recurring shifts, and time off. | Dealership-scoped application use cases and PostgreSQL constraints. |
| Customer and vehicle record | Authorized employees can create, find, and maintain customers and their vehicles; vehicle operations enforce the relevant dealership/customer boundary. | Customer and vehicle application and HTTP tests. |
| Appointment scheduling | An authorized dealership employee schedules a customer vehicle against a service type, technician, and bay. The system checks tenant scope, resource activity, required skills and capabilities, local operating hours, technician shift, and time off. | Transactional scheduling repository plus application/domain tests. |
| Appointment lifecycle | An appointment moves through `requested → checked_in → in_progress → completed`, or is cancelled with a mandatory reason. Invalid or stale transitions return a conflict rather than silently corrupting the workflow. | Domain lifecycle rules, row locking, and state-transition tests. |
| Operational visibility | Employees can view technician schedules; appointment changes create immutable audit events that record actor, time, and before/after state. | Scheduler query endpoint and append-only audit-event trigger. |

### Authorization model

Two scopes are intentionally separate:

- **Global platform roles** (`user`, `admin`, `superadmin`) govern platform-level administration, including dealership creation.
- **Dealership roles** (`admin`, `staff`, `dealer`, `technician`) govern day-to-day work within one dealership.

This prevents a user who is valid at one dealership from gaining implicit access to another. The server resolves the actor and dealership scope; it never trusts a client-supplied user or dealership identity for authorization.

## Non-functional requirements and acceptance criteria

| Requirement | Decision / acceptance criterion |
|---|---|
| Correctness under concurrency | A technician and a service bay must never be double-booked for active work. PostgreSQL exclusion constraints are the final authority, not only application checks. Conflicts are returned as HTTP `409`. Adjacent bookings are permitted through half-open time intervals. |
| Data integrity | Appointment creation, resource reservations, and audit event are written in one serializable transaction. Foreign keys, check constraints, soft deletion, row locks, and trigger checks prevent invalid persisted state. |
| Security and privacy | All scheduler APIs require bearer authentication. JWTs use RS256 and have a 15-minute access-token lifetime; refresh tokens are 7 days. Production keys must come from a secret manager, TLS must terminate with production certificates, and development secrets must never be deployed. |
| Tenant isolation | Every dealership-owned action is authorized against the actor’s dealership membership, and appointment transitions load the appointment with the dealership predicate under lock. |
| Auditability | Appointment audit rows are append-only at database level. Cancellation captures a reason; lifecycle events capture the actor and timestamp. |
| Maintainability | Code is partitioned into domain, application, adapter, and HTTP API layers. HTTP contracts originate in OpenAPI; SQL access originates in checked-in sqlc queries. Database, API, and domain models are deliberately separate. |
| Operability | The service exposes `/health`, structured/correlation-aware logging, embedded versioned migrations, Docker Compose local runtime, deterministic development seed data, and both HTTP and development TLS listeners. |
| Testability | Domain and application behavior is unit tested without real infrastructure; HTTP mappings and authorization are tested at the handler boundary. `go test ./...` passes as of this review. |
| Performance and scale | The initial workload is relational and correctness-sensitive, not write-heavy. PostgreSQL provides the joins, transactions, range constraints, and indexing needed before introducing cache or distributed-system complexity. Performance SLOs and load-test thresholds will be agreed in the later system-design review. |

## Architecture and technical decisions

### 1. Modular monolith, not premature microservices

The service contains two bounded contexts: `auth` and `appointment_scheduler`. Each has independent domain, application, database-adapter, and HTTP API packages. The scheduler consumes authentication only through the published auth module contract.

This delivers practical separation of ownership and dependency direction without distributed transactions, duplicated deployments, network failure modes, or a cross-service identity protocol. Most importantly, booking and capacity reservation stay atomic. If a future scale or organizational boundary requires extraction, these explicit module contracts are a safer starting point than a tightly coupled CRUD monolith.

### 2. PostgreSQL is the system of record

The scheduling problem is fundamentally relational: service types require skills and bay capabilities; technicians work shifts and take time off; an appointment consumes both a technician and a bay. PostgreSQL is selected because it can enforce those relationships and temporal exclusion constraints atomically.

The design does **not** add Redis or a NoSQL database without a measured problem. Redis may later cache read-heavy availability views; append-only audit/history may later be partitioned or archived. Neither should become a second source of truth for booking availability.

### 3. Correctness is enforced twice

The application validates business eligibility for actionable errors. PostgreSQL independently enforces final temporal conflicts and time-off protection within the write transaction. This defence-in-depth model protects against concurrent requests, retries, and future code paths that might otherwise bypass an application-level check.

### 4. Contract-first delivery and generated boundaries

OpenAPI specifications are the hand-maintained HTTP source of truth, with generated server bindings. SQL queries are the source for generated sqlc data-access bindings. This reduces transport and database mapping mistakes while keeping generated code out of business logic. Human-reviewed application and domain code remains responsible for policy.

### 5. Security boundary appropriate to an internal tool

The current auth module is suitable for the internal-workforce scope when deployed behind normal enterprise controls: TLS, secret management, least-privilege database access, logging/monitoring, and optionally network allow-listing/VPN. A customer-facing portal or cross-application SSO requirement should trigger an identity-platform assessment (for example, Keycloak or the organization’s existing IdP) rather than extending this internal module indefinitely.

### 6. Front-end is intentionally decoupled

The API supports a React/Next.js, Nuxt, or Angular operational UI. Team capability should decide the framework. A future public landing site can be static and CDN-cached; authenticated operations should remain dynamic and must not cache personalized or sensitive responses at the CDN.

## Hard parts solved

1. **Preventing double booking under concurrent requests.** A booking reserves both technician and bay in the same serializable transaction. Database exclusion constraints protect the appointment and reservation ledgers, and a time-off trigger uses a transaction-scoped advisory lock to close a concurrency gap.
2. **Making local workshop time safe globally.** Storage uses UTC timestamps; schedule validation converts against the dealership timezone to test operation hours and technician shifts correctly.
3. **Keeping lifecycle history trustworthy.** State transitions are explicit, invalid transitions fail, cancellation requires a reason, and database-triggered append-only audit records make later investigation possible.
4. **Balancing tenant isolation with shared operations.** The shared deployment retains a dealership boundary in authorization and data access, allowing efficient operations without treating the entire platform as one tenant.
5. **Protecting privacy while retaining usable account lookup.** Reversible encryption serves authorized operational use; an independently keyed deterministic HMAC supports duplicate detection and lookup without storing searchable plaintext email.
6. Access_Token verifying will be handled in every component instead of call auth module.

## AI engineering, verification, and ownership

AI accelerated research, scaffolding, and repetitive contract/model work; it was not treated as an authority. The implementation process is designed to retain human ownership:

- Business rules were expressed in domain/application code and reviewed as explicit invariants, rather than accepted as bulk-generated CRUD behavior.
- OpenAPI and SQL remain readable source artifacts; generated outputs are derived and inspected, not manually edited.
- Tests cover appointment transitions, authorization decisions, scheduler and customer/vehicle operations, encryption, token issuance, HTTP error mapping, TLS, configuration, and common error behavior.
- The complete Go suite was run successfully during this documentation review: `cd dealership && go test ./...`.
- The remaining production verification is intentionally concrete: run PostgreSQL integration tests for constraints/triggers and concurrent booking, add load testing for the agreed capacity model, conduct security review and secret-management validation, and prove backup restore before launch.

## Known gaps, decisions required, and recommended next gate

| Item | Current position | Decision / next action |
|---|---|---|
| Booking retry idempotency | The schema has an idempotency table, but the public booking API does not yet accept/enforce an idempotency key. | Add an `Idempotency-Key` contract and transactional replay behavior before production. |
| Authorization policy | The implemented roles are clear; some business ownership decisions remain open, such as who may create/edit service types, skills, capabilities, and bays. | Product/operations leadership approves a role-permission matrix; encode it in tests and OpenAPI descriptions. |
| Auth for external customers | The current module is designed for internal operations, not consumer identity federation. | Reuse enterprise IdP or evaluate Keycloak/OIDC before customer self-service is introduced. |
| Production resilience | Local Compose and health checks are present; managed hosting, observability targets, backup recovery, and deployment controls are not the subject of this assessment. | Approve these in the system-design review and validate through a launch-readiness checklist. |
| Availability selection | The API accepts a selected technician and bay; it does not yet expose a recommendation/slot-search engine. | Validate advisor workflow first; add deterministic availability search only when UX requires it. |
| Historical data growth | Audit/history is relational and append-only. | Retain initially; partition/archive based on measured retention, query, and compliance needs—not speculative NoSQL migration. |

## Recommendation

Approve the implementation as a **correctness-first internal scheduling foundation** and proceed to the system-design review with the five gates above. The most valuable next investment is not microservices or additional databases: it is completing idempotent booking, ratifying role ownership, and proving production readiness through integration, concurrency, recovery, and security verification.
