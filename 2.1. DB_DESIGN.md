# Appointment scheduler database design

The initial migration creates the `appointment_scheduler` PostgreSQL schema. All tables use UUID primary keys generated with `gen_random_uuid()`. Timestamps use `timestamptz` unless stated otherwise. Tables that have `deleted_at` use soft deletion; active-row uniqueness and scheduling rules generally exclude deleted rows.

The migration enables the `pgcrypto` and `btree_gist` extensions.

## Dealership and access tables

| Column | Type | Rules |
|---|---|---|
| `dealership_id` | `uuid` | PK, generated by default |
| `name` | `varchar(255)` | required |

| `address` | `text` | required |

| `deleted_at` | `timestamptz` | nullable |
| `updated_at` | `timestamptz` | required, default current timestamp |

### `dealership_operation_time`

| Column | Type | Rules |
|---|---|---|
| `dealership_operation_time_id` | `uuid` | PK, generated by default |
| `dealership_id` | `uuid` | required, FK → `dealerships` |
| `day_of_week` | `smallint` | required, `1` Monday through `7` Sunday |
| `opens_at` | `time` | required |
| `closes_at` | `time` | required, later than `opens_at` |
| `created_at` | `timestamptz` | required, default current timestamp |
| `updated_at` | `timestamptz` | required, default current timestamp |

The migration prevents overlapping operating intervals for the same dealership and day with `dealership_operation_time_no_overlap`. It also creates `dealership_operation_time_dealership_day_opens_at_idx` on `(dealership_id, day_of_week, opens_at)`. There is no uniqueness constraint limiting a dealership to one interval per day.

### `roles`

|---|---|---|

### `user_roles`

| Column | Type | Rules |
|---|---|---|
| `user_role_id` | `uuid` | PK, generated by default |

`UNIQUE (user_id, role_id)` prevents duplicate assignments. The uniqueness constraint includes soft-deleted rows because it is a table constraint, not a partial index.

## Customers and vehicles

## Appointments and supporting tables

### `appointments`

| Column | Type | Rules |
|---|---|---|
| `appointment_id` | `uuid` | PK, generated by default |
| `reference_code` | `varchar(50)` | required, unique |
| `customer_id` | `uuid` | required, FK → `customers` |
| `vehicle_id` | `uuid` | required, FK → `vehicles` |
| `dealership_id` | `uuid` | required, FK → `dealerships` |
| `service_type_id` | `uuid` | required, FK → `service_types` |
| `technician_id` | `uuid` | required, FK → `technicians` |
| `service_bay_id` | `uuid` | required, FK → `service_bays` |
| `starts_at` | `timestamptz` | required |
| `ends_at` | `timestamptz` | required, later than `starts_at` |
| `status` | `varchar(32)` | required; `requested`, `checked_in`, `in_progress`, `completed`, or `cancelled` |
| `notes` | `text` | nullable |
| `created_by_user_id` | `uuid` | required, FK → `users` |
| `cancelled_by_user_id` | `uuid` | nullable, FK → `users` |
| `cancellation_reason` | `text` | nullable; required when cancelled |
| `created_at` | `timestamptz` | required, default current timestamp |
| `deleted_at` | `timestamptz` | nullable |
| `updated_at` | `timestamptz` | required, default current timestamp |
| `cancelled_at` | `timestamptz` | nullable |
| `checked_in_at` | `timestamptz` | nullable |
| `in_progress_at` | `timestamptz` | nullable |
| `started_at` | `timestamptz` | nullable |
| `completed_at` | `timestamptz` | nullable |
| `actual_ends_at` | `timestamptz` | nullable |
| `planned_duration_minutes` | `integer` | nullable; positive when present |

The migration creates `appointments_dealership_starts_at_idx` and an active-future technician index. Active appointments (`requested`, `checked_in`, or `in_progress`) cannot overlap for the same technician or service bay through exclusion constraints. Deleted appointments and terminal statuses do not participate in those constraints.

The migration does not enforce that the vehicle belongs to the customer, or that all appointment resources belong to the appointment’s dealership, with foreign keys. Those relationships must be validated by application logic in the booking transaction.

An `appointments_reject_technician_time_off` trigger rejects active appointments that overlap active technician time off. It takes a transaction advisory lock per technician before checking for the overlap.

## Scheduling interval semantics

All interval exclusion constraints use half-open ranges, `[)`. Therefore an interval ending at `10:00` does not conflict with another interval starting at `10:00`. The migration applies this to dealership operation times, technician shifts, technician time off, appointments, and resource reservations.
