# Appointment Scheduler — System Design

## Purpose and scope

The Appointment Scheduler is a multi-dealership Go service for booking and operating vehicle-service appointments. It owns dealership scheduling data, customers and vehicles, service configuration, bays, technicians, availability, appointment lifecycle, reservations, and audit history. Redis provides global HTTP idempotency.

This replaces the previous per-dealership-service assumption. A **single shared deployment** serves 100 dealerships worldwide. It is a modular Go monolith with `auth` and `appointment_scheduler` bounded contexts: authentication is owned by `auth`, while dealership-scoped authorization is owned by the scheduler.

The OpenAPI document at `dealership/modules/appointment_scheduler/api/http/openapi.yaml` is the HTTP-contract source of truth. `DB_design.md` is the persistence source of truth.

## Capacity model

| Item | Per dealership | Global (100 dealerships) |
|---|---:|---:|
| Local service-area population | 10,000 | 1,000,000 |
| Employees | 15 | 1,500 |
| Admins / staff / dealers / technicians | 1 / 2 / 2 / 10 | 100 / 200 / 200 / 1,000 |
| Employees concurrently working per shift | 7 | Up to 700 |

The seven-person figure is a local shift-concurrency constraint, not a fixed count of bookable technicians. Bookable capacity is derived from active technician shifts, skills, bay capabilities, dealership operating hours, time off, and reservations.

Population does not itself establish vehicle demand. For an explicit, conservative planning scenario, assume **one scheduled visit per resident per year** until vehicle-parc and visit-rate data is available.

| Metric | Estimate | Basis |
|---|---:|---|
| Appointments/year | 1,000,000 | 100 × 10,000 × 1 visit |
| Appointments/dealership/year | 10,000 | 1,000,000 ÷ 100 |
| Appointments/business day | ~3,570 globally; ~36/dealership | 280 business days/year |
| Average booking writes | ~0.5 RPS globally | Spread over 8 business hours |
| Design peak | 25 API RPS globally; 5 RPS/dealership | Calendar refreshes, shift starts, retries, 5× headroom |
| Five-year appointment history | 5,000,000 appointments | Before archival |
| Five-year resource reservations | 10,000,000 rows | Technician + bay per appointment |
| Five-year audit events | 15–25 million rows | Create, lifecycle, and edits |

This is a correctness-first workload: calendar and availability reads dominate, while concurrent claims on a resource must never double-book it.

## Architecture

~~~mermaid
flowchart LR
    U[Dealership users<br/>up to 700 on shift] --> LB[HTTPS load balancer]
    LB --> A1[Go API 1<br/>auth + scheduler modules]
    LB --> A2[Go API 2<br/>auth + scheduler modules]
    A1 --> PG[(Managed PostgreSQL<br/>appointment_scheduler)]
    A2 --> PG
    A1 -->|/metrics scrape| PR[Prometheus]
    A2 -->|/metrics scrape| PR
    PR --> GR[Grafana]
    A1 -->|OTLP/HTTP traces| J[Jaeger]
    A2 -->|OTLP/HTTP traces| J
    PG --> B[Backups and PITR]
~~~

Run two or more stateless API instances behind a load balancer. Start with one managed PostgreSQL HA primary. Do not split the system or database by dealership initially: the scheduling set is modest and shared infrastructure is simpler to operate. Add a read replica only when observed availability/calendar reads justify it; booking validation and all availability claims continue to read and write the primary.

~~~mermaid
flowchart TB
    HTTP[HTTP adapter<br/>Echo + OpenAPI types] --> APP[Application services<br/>commands and queries]
    APP --> DOMAIN[Domain model<br/>invariants and transitions]
    APP --> PORTS[Consumer-owned ports]
    DB[PostgreSQL adapter<br/>pgx + sqlc] --> PORTS
    MAIN[Composition root] --> HTTP
    MAIN --> DB
~~~

- The auth module authenticates the bearer token and exposes only a published module contract to the scheduler; the scheduler does not query auth persistence directly.
- HTTP adapters parse the generated OpenAPI contract, obtain the authenticated identity, and map errors to HTTP.
- Application services orchestrate commands, queries, and transaction boundaries.
- The domain model owns state-transition and business invariants.
- PostgreSQL adapters run sqlc queries and translate constraints into application errors.
- The composition root wires modules, migrations, contracts, database pool, and routes; it contains no booking policy.

A dealership is the tenant boundary. All dealership-owned reads and writes use the actor ID from the verified token plus a dealership predicate; clients cannot supply an effective actor or bypass the dealership scope. The scheduler’s `users`, `roles`, and `user_roles` tables are deliberately its local authorization projection: they associate an authenticated auth-module user ID with a dealership role (`admin`, `staff`, `dealer`, or `technician`) without coupling the scheduler domain to auth tables. Global platform roles (`user`, `admin`, `superadmin`) remain owned by auth. Global scheduler reference data includes skills and bay capabilities. Customer identity is global, but the current `customer_dealerships` schema links one customer to one dealership; supporting shared customers is a future schema change.

For the internal-workforce scope, auth issues RS256 JWT access tokens (15 minutes) and refresh tokens (7 days). The scheduler receives the verified user ID through the auth module’s published contract, then makes its own dealership-role decision. This preserves scheduler ownership of its authorization rules while keeping credentials, token lifecycle, and global roles out of its domain.

## Technology choices and rationale

| Technology | Role | Why it is chosen |
|---|---|---|
| Go | Service runtime | A compact, efficient runtime with strong standard-library HTTP support and straightforward concurrent request handling. It matches the existing implementation and keeps deployment units small. |
| Modular monolith | Deployment architecture | Auth and scheduling run in one deployable while remaining bounded modules. This keeps identity lookup, booking, reservations, and audit writes local, avoiding distributed transactions at the current scale. |
| Echo + OpenAPI | HTTP transport and contract | Echo provides the HTTP adapter; OpenAPI is the hand-maintained contract from which bindings and transport models are generated. This avoids duplicate hand-maintained API types. |
| PostgreSQL | System of record | Relational joins, ACID transactions, range exclusion constraints, triggers, and indexes directly address scheduling correctness. It is the sole source of truth for bookings. |
| pgx + sqlc | Database access | pgx is the PostgreSQL driver; sqlc generates typed bindings from reviewed SQL. Queries stay explicit without spreading SQL scanning and mapping code through application services. |
| Managed PostgreSQL HA, backups, and PITR | Persistence operation | Provides failover, managed patching, durable backups, and point-in-time recovery without operating a database cluster ourselves. |
| Docker Compose and versioned SQL migrations | Local development and delivery | Reproducible local PostgreSQL environments and versioned schema changes make constraint and integration testing practical. |
| OpenTelemetry, Prometheus, Grafana, and Jaeger | Operational signals | OpenTelemetry instruments HTTP and PostgreSQL, Prometheus stores scraped metrics, Grafana presents metric dashboards, and Jaeger receives distributed traces. The local Compose stack validates the full path without making the domain depend on a vendor. |

Redis, a message broker, and a NoSQL store are intentionally not part of the initial design. A cache may later hold derived availability reads, but never becomes the booking authority; it must be invalidated on scheduling/configuration changes and a cache miss or outage must fall back to PostgreSQL.

## Availability and read consistency

Availability reads derive candidate slots from operating hours, active service types, qualified technicians, compatible bays, shifts, time off, and active reservations. They may be served from the primary database initially and are advisory only: the scheduling command repeats validation and claims both resources transactionally on the primary. This means a displayed slot can become unavailable before submission, in which case the API returns `409 Conflict` rather than creating an invalid appointment.

Do not cache availability initially. If measurements later justify caching, use a short TTL and dealership-scoped keys, invalidate on appointment/resource/configuration changes, and label cached results with their generation time. Read replicas may serve non-authoritative calendar/history reads, but not booking validation or slot claims, because replica lag could advertise an already-booked resource.

## Scheduling and persistence

~~~mermaid
sequenceDiagram
    actor Advisor
    participant API as Scheduler API
    participant App as Appointment service
    participant DB as PostgreSQL
    Advisor->>API: Schedule appointment
    API->>App: command + trusted actor context
    App->>DB: begin transaction
    App->>DB: validate dealership, customer/vehicle, duration, hours, skills, bay capabilities, shift and time off
    App->>DB: create appointment, two reservations, and audit event
    DB->>DB: enforce exclusion constraints and time-off trigger
    alt success
        DB-->>App: commit
        App-->>API: 201 Created
    else replay / conflict / invalid request
        DB-->>App: prior result / rollback
        App-->>API: 200 / 409 / 422
    end
~~~

| Concern | Tables |
|---|---|
| Tenant and staff | `dealerships`, `dealership_operation_time`, `users`, `roles`, `user_roles` |
| Customer fleet | `customers`, `customer_dealerships`, `vehicles` |
| Service catalogue | `service_types`, `skills`, `service_type_required_skills`, `bay_capabilities`, `service_type_required_bay_capabilities` |
| Workshop resources | `service_bays`, `service_bay_capabilities`, `technicians`, `technician_skills`, `technician_shifts`, `technician_time_off` |
| Scheduling ledger | `appointments`, `appointment_resource_reservations`, `appointment_audit_events` |

Application code must validate cross-table relationships not enforced by foreign keys: vehicle ownership; dealership membership of customer, service type, bay, technician, and actor; all required skills/capabilities; operating hours; shifts; and time off.

PostgreSQL is the final concurrency guarantee. Active appointments and unreleased active reservations use half-open `[)` exclusion ranges, so an appointment ending at 10:00 does not conflict with one starting at 10:00. The time-off trigger rejects overlapping active appointments under a per-technician advisory lock. Constraint conflicts are normal `409 Conflict` outcomes.

~~~mermaid
stateDiagram-v2
    [*] --> requested
    requested --> checked_in
    checked_in --> in_progress
    in_progress --> completed
    requested --> cancelled
    checked_in --> cancelled
    completed --> [*]
    cancelled --> [*]
~~~

`requested`, `checked_in`, and `in_progress` reserve capacity; `completed` and `cancelled` release it. Cancellation requires a reason. Every transition appends an immutable audit event.

## Operations and production sizing

| Component | Initial production allocation | Scale trigger |
|---|---|---|
| Scheduler API | 2 instances, 1 vCPU, 512 MiB–1 GiB each | Sustained >25 RPS, CPU >60%, or p95 breach |
| PostgreSQL | HA managed, 2–4 vCPU, 8–16 GiB RAM, 200 GB SSD | Storage >70%, pool saturation, or p95 query breach |
| DB connections | 10 per API process initially | Change only from observed pool/database use |
| Recovery | Daily backup + point-in-time recovery; scheduled restore tests | Required before launch |

- Store all instants in UTC `timestamptz`; convert at the boundary using `dealerships.timezone`.
- Require the global idempotency header for every unsafe request; Redis rejects a replayed method-route-key combination.
- Choose availability deterministically (for example, least-loaded qualified technician then bay code).
- Test database constraints, time-off trigger, tenancy, idempotency, and concurrent booking in PostgreSQL integration tests. Load-test 25 RPS globally with an availability-heavy mix and 5 RPS concentrated at one dealership.
- Review these estimates after three months of observed traffic and archive/partition append-only history before materially increasing storage.

## Observability and operational response

### Logs, metrics, and traces

The local stack is declared in `docker-compose.yaml`: Prometheus (`v2.53.5`), Grafana (`v10.4.19`), an OpenTelemetry Collector, and Jaeger all-in-one (`v1.68.0`). Prometheus scrapes the service's `GET /metrics` endpoint every 15 seconds. Grafana is provisioned with Prometheus as its default datasource and with a dealership overview dashboard. The service exports OTLP/HTTP traces to the endpoint configured by `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`; Docker Compose routes them through the Collector to Jaeger, and `OTEL_SERVICE_NAME=dealership` identifies the service.

- The current implementation exports OpenTelemetry Prometheus metrics through `/metrics`, including Go/process metrics and PostgreSQL pool metrics registered by `otelpgx`. Prometheus is the metric store; Grafana queries it for dashboards.
- HTTP requests are instrumented with `otelhttp`; PostgreSQL calls are instrumented with `otelpgx`. W3C `traceparent` context is propagated, SQL statement text is deliberately excluded from trace attributes, and the trace provider batches OTLP/HTTP exports to Jaeger. Use Jaeger to inspect an HTTP request and its database spans.
- Appointment scheduling and lifecycle transitions create low-cardinality outcome counters, duration histograms, and application spans. Continue adding idempotency-replay and availability-query signals as those public capabilities are introduced. Do not use customer, vehicle, appointment, actor, or dealership IDs as metric labels.
- Use structured `slog` logs and never log raw bearer tokens, passwords, encrypted customer fields, request bodies, response bodies, or unredacted PII. Request logs include correlation ID, trace ID/span ID, route, method, status, and duration. A centralized log backend and retention/access policy remain production work; audit events remain business evidence, not a replacement for operational logs.

### Production telemetry completion

- Resource attributes include `service.name`, `service.version`, `deployment.environment.name`, and deployment region. Populate them from deployment configuration, not request data. Add an instance identifier in the production deployment. Do not add tenant, user, appointment, or vehicle identifiers as resource attributes or metric labels.
- Expand current booking/lifecycle telemetry with availability-search, eligibility-validation, idempotency-replay, and dependency-outcome signals. Labels must be a small, bounded set such as route, operation, outcome, and HTTP status class.
- Expand application spans to authentication, authorization, availability calculation, resource selection, and idempotency lookup. Record safe outcome attributes such as `appointment.operation`, `booking.outcome`, and `conflict.resource_type`; keep opaque IDs only in protected logs and audit records, never in metric labels or span attributes.
- The HTTP boundary accepts or generates a correlation ID, returns it in a response header, and logs it with trace ID/span ID, route, status, and duration. Export structured logs to the organization’s centralized log backend with access control and a retention policy.
- OTLP traces already pass through an OpenTelemetry Collector. Before production, add collector retries, bounded queues, attribute filtering, rate limits, and tail-based sampling: retain all error/conflict/slow traces while sampling routine successful traffic. Telemetry outages must never block booking.
- Keep Prometheus scrape targets private, authenticated where the platform supports it, and protected by network policy/TLS. Add managed PostgreSQL metrics for availability, replication/failover, connections, storage, locks, and slow queries; application pool metrics alone cannot show all database failure modes.
- Define retention and cost controls: Prometheus retention/remote-write policy, Jaeger trace retention and storage backend, log retention, cardinality budgets, and a periodic review of telemetry volume. Jaeger all-in-one with ephemeral local storage is development-only and is not a production trace backend.

### Dashboards, SLOs, and alerts

Grafana has the Prometheus datasource and a dealership overview dashboard provisioned. Before production, extend dashboard coverage to API traffic/error/latency, PostgreSQL connection-pool health, availability latency, migration state, and backup/restore status. Breakdown by dealership is permitted only where it does not expose customer data and must avoid high-cardinality Prometheus labels. Initial objectives are: 99.9% successful API availability per calendar month excluding planned maintenance; p95 availability reads below 500 ms; p95 successful booking responses below 1 s; and zero confirmed double-bookings.

Prometheus alert rules cover a missing service scrape target and booking errors; Alertmanager/on-call delivery is still required before production. Add rules for sustained 5xx or SLO burn, database failover/unavailability, connection-pool saturation, failed migrations, failed backups, missed restore tests, double-booking invariant violations, and telemetry-exporter queue drops or failures. A booking-conflict increase is normally a product signal; alert only on an unusual baseline deviation. Every alert must link to a runbook and dashboard, and incidents must preserve the trace ID and appointment/audit identifiers needed for investigation.

## Resilience, security, and recovery

- Terminate TLS at the load balancer and use production certificates. The auth module verifies bearer tokens; auth secrets, encryption keys, and database credentials are stored in a secret manager and rotated through a documented runbook.
- Apply connection, request, and database statement timeouts. Retry only idempotent reads automatically; a client retries a failed booking with the same idempotency key. Do not automatically retry a transaction after an ambiguous booking outcome without resolving its outcome.
- Treat the managed PostgreSQL primary as a dependency: if it is unavailable, fail writes and authoritative availability reads explicitly with a retriable `503`; do not degrade into uncoordinated local reservations. `/health` is a process-liveness check and `/readyz` checks database connectivity. Keep readiness monitoring off public paths where platform policy requires.
- Start with daily backups and point-in-time recovery. Before launch, define and verify RPO/RTO with the hosting provider, run a scheduled restore test, and alert on its failure. Restrict database network access and use least-privilege application and migration credentials.

## Assumptions and decisions to revisit

| Topic | Current decision | Trigger to revisit |
|---|---|---|
| Tenant isolation | Application authorization plus dealership predicates; no PostgreSQL row-level security initially. | A new database access path, compliance requirement, or repeated tenancy defect. |
| Customer ownership | A customer is currently linked to one dealership. | A business requirement for shared fleet/customer records. |
| Availability UX | Advisor selects resources; deterministic recommendation is a future option. | Evidence that manual resource selection slows booking or causes errors. |
| Historical retention | Retain relational audit/history initially; partition or archive from measured use and retention policy. | Storage, query, or legal-retention thresholds. |
| Customer-facing access | Internal employee tool only. | Public portal, SSO, notification, payment, or dealer-management-system integration. |

## GenAI assistance in the design phase

GenAI was used as a drafting and review aid: it helped organize the architecture and sequence diagrams, challenge capacity and failure assumptions, and identify concurrency, observability, and documentation gaps. It was not treated as an implementation authority. The design was checked against the reviewed OpenAPI contract, the SQL schema and constraints, module boundaries, and automated tests; final business rules, technology choices, and operational acceptance criteria remain human-owned.

## Delivery rules

- Generate HTTP interfaces and transport models from OpenAPI; do not hand-maintain duplicate contract types.
- Use SQL migrations and sqlc for data access; keep scheduling decisions in domain/application code.
- Ensure tenant-scoped repository queries and `404` behavior for out-of-scope resources.
- Run migration, unit, PostgreSQL integration, and concurrent-booking tests in CI.
